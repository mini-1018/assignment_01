# 프런트엔드 검증 절차

## 검증의 원칙

**파일이 있다는 것은 동작한다는 뜻이 아니다.** 이 구성에서 나오는 결함의 대부분은 파일이 전부 제자리에 있는 상태에서 발생한다. 훅은 `image_url`을 반환하는데 카드가 `imageUrl`을 읽거나, RLS 정책이 없어 빈 배열이 오거나, 조회가 서버 컴포넌트에서 실행돼 CSR 요건을 벗어나 있다. 세 경우 모두 빌드는 통과한다.

그래서 검증은 **실행**과 **대조**로 한다. 명령을 실제로 돌리고, 두 파일의 값을 눈으로 맞춘다.

**검사 범위:** `_workspace/00_request.md`의 「화면 범위」 표를 먼저 읽는다. B·C·D(데이터 대조, CSR, 화면 상태)는 시안 기반 화면에만 적용한다. A(실행 검사)는 보류 화면을 포함한 전체 코드에 돌린다. 보류 화면에서 나온 결함은 보고서에 「범위 외」로 따로 적고 심각도를 매기지 않는다. 단, 빌드를 깨뜨리면 배포를 막으므로 높음으로 분류한다.

**검사 시점:** 전체가 끝난 뒤 한 번이 아니라, 모듈 하나(화면 하나 또는 훅 하나)가 끝날 때마다 검사한다. 결함이 쌓이면 어느 변경이 원인인지 분리할 수 없다.

## A. 실행 검사

```bash
npx tsc --noEmit                                                   # 타입
npx next lint                                                      # 린트
node .claude/skills/fsd-architecture/scripts/check-layer-imports.mjs   # 레이어·import 위반, 폴더 구조(알 수 없는 폴더·공개 API 누락·세그먼트 이름)
npm test                                                           # 단위·훅·위젯 테스트
rm -rf .next && npx next build                                     # 프로덕션 빌드(오래된 캐시 제거 후)
```

- `.next`를 지우고 빌드한다. 라우트를 지우거나 옮긴 뒤에는 `.next/types`가 없는 파일을 가리켜 `tsc`까지 실패한다. 이 오류는 코드 결함이 아니므로 캐시를 지우고 다시 돌린 결과로 판정한다.
- 테스트가 통과했다고 해당 기능을 검증한 것으로 보지 않는다. 계약(`03_data_contract.md`)의 훅과 화면 상태마다 대응하는 테스트가 있는지 대조하고, 없는 항목은 「테스트 공백」으로 보고한다.

- 각 명령의 출력 원문을 보고서 근거로 남긴다. 실행하지 않은 검사를 통과로 적지 않는다.
- 빌드는 마지막에 한 번 돌린다. 앞의 세 검사가 실패하면 빌드는 볼 필요가 없다.
- 명령이 환경 문제로 실행되지 않으면 `실패`가 아니라 `검사 불가`로 분류하고 무엇을 확인하지 못했는지 적는다.

## B. 데이터 흐름 대조 (가장 중요)

`_workspace/03_data_contract.md`의 훅 계약과 실제 코드를 대조한다.

훅마다 다음 네 가지를 확인한다.

1. **필드명 일치** — 훅의 `select(...)` 컬럼, 반환 타입 필드, 컴포넌트가 읽는 프로퍼티가 같은 철자인가. 스네이크 케이스와 카멜 케이스가 섞였는지 특히 본다.

   ```bash
   grep -rn "select(" src/entities/*/api/
   grep -rn "\.title\|\.image_url\|\.imageUrl" src/
   ```

2. **오류 검사 존재** — 모든 `queryFn`에 `if (error) throw error;`가 있는가.

   ```bash
   grep -rLn "if (error)" src/entities/*/api/*.ts
   ```

3. **타입 출처** — 컴포넌트가 화면 쪽에서 직접 정의한 타입을 쓰고 있지 않은가. 엔티티 타입이나 생성된 Supabase 타입을 써야 한다.

4. **테이블·컬럼 실재** — 훅이 조회하는 테이블과 컬럼이 `supabase/migrations/`에 실제로 있는가. 계약 문서가 아니라 마이그레이션 SQL과 대조한다.

## C. CSR 요건 확인

사용자가 요구한 것은 **브라우저에서 불러와 화면에 보여지는 것**이다.

- 데이터를 조회하는 파일 맨 위에 `'use client'`가 있는가.
- `app/**/page.tsx`에서 직접 `supabase.from(...)`을 호출하고 있지 않은가. 있으면 CSR 요건 위반이다.

  ```bash
  grep -rn "supabase" app/ || echo "라우트에 직접 조회 없음 — 정상"
  ```

- 개발 서버를 띄운 상태라면 네트워크 요청으로 확인한다. `/rest/v1/`로 나가는 요청이 없으면 브라우저에서 조회하지 않은 것이다.

## D. 화면 상태 확인

화면마다 세 상태가 모두 구현돼 있는가.

| 상태 | 확인 방법 |
| --- | --- |
| 로딩 | `isPending` 분기와 스켈레톤/인디케이터가 있는가 |
| 빈 데이터 | 배열이 비었을 때의 분기가 있는가 |
| 오류 | `error` 분기와 재시도 수단이 있는가 |

`isPending` 분기가 없으면 첫 렌더에서 `undefined`를 읽어 런타임 오류가 난다. 데이터가 빨라 눈에 안 띌 뿐 결함이다.

## E. 배포 전 추가 점검

- `.env.local`이 추적되지 않는가 (`git check-ignore -v .env.local`).
- `NEXT_PUBLIC_`이 붙은 변수에 service_role 키가 없는가.
- `.env.example`에 필요한 변수 이름이 모두 있는가.
- 하드코딩된 `localhost` URL이 남아 있지 않은가.

## 보고서 형식

`_workspace/04_qa_report.md`:

```markdown
# QA 보고서 — {날짜} / 대상: {모듈 또는 전체}

## 요약
- 실행한 검사: {목록}
- 위반 {n}건 / 경고 {n}건 / 검사 불가 {n}건

## 결함
| 심각도 | 위치 | 증상 | 재현 방법 | 근거 |
| --- | --- | --- | --- | --- |
| 높음 | src/views/home/Home.tsx:24 | 상품 이미지가 비어 렌더링됨 | 홈 진입 | 훅은 image_url 반환, 컴포넌트는 imageUrl 사용 |

## 통과 항목
| 검사 | 명령 | 결과 |

## 범위 외(보류 화면)
| 화면 | 발견 사항 |

## 검사하지 못한 범위
- {무엇을 왜 확인하지 못했는지}
```

심각도 기준: **높음** = 사용자가 보는 화면이 잘못되거나 데이터가 안 나온다. **중간** = 구조·타입 규칙 위반으로 확장 시 문제가 된다. **낮음** = 개선 제안.

소스 코드는 고치지 않는다. 고치는 일은 구현 에이전트의 몫이고, 검증자가 고치면 아무도 검증하지 않은 코드가 남는다.
