# Next.js FSD 앱 오케스트레이터

## 실행 모드: 혼합

| 단계 | 실행 모드 | 선택 이유 |
| --- | --- | --- |
| 0 준비 | 메인 에이전트 | 입력 확인과 재실행 판단은 사용자와 직접 주고받아야 한다 |
| 1 구조 설계 · 2 디자인 추출 | 서브에이전트 위임(병렬) | 서로 입력이 겹치지 않는 독립 작업이고 결과만 받으면 된다 |
| 3 구현 | 지속형 에이전트 협업 | UI와 데이터가 필드 이름과 훅 계약을 계속 맞춰야 한다. 한 번 호출로는 이 협상이 안 된다 |
| 4 검증 | 서브에이전트 위임 | 독립 검증자 한 명이 실행 결과로 판정하면 된다 |
| 5 배포 | 서브에이전트 위임 | 정해진 CLI 절차이며 사용자 승인이 앞선다 |

## 작업 절차

### 0단계: 준비 (메인 에이전트)

**재실행 판단**

1. `_workspace/`가 없으면 → 처음부터 실행한다.
2. 있고 일부 수정 요청이면 → 해당 단계만 다시 실행한다. 아래 표를 따른다.
3. 있고 새 디자인이나 새 요구사항을 받았으면 → `_workspace/`를 `_workspace_{YYYYMMDD-HHmm}/`로 옮기고 새로 실행한다.

| 요청 | 다시 실행할 단계 |
| --- | --- |
| "이 화면 디자인 바뀌었어" | 2(해당 화면만) → 3(UI) → 4 |
| "필드 추가해줘" | 3(데이터 → UI 순서로) → 4 |
| "구조를 바꾸고 싶어" | 1 → 영향받는 3 → 4 |
| "배포만 다시" | 5 |

**입력 확인**

다음을 확인하고, 없으면 사용자에게 한 번에 모아서 묻는다.

| 입력 | 필요 단계 | 없을 때 |
| --- | --- | --- |
| Figma 파일 URL | 2 | 2단계를 건너뛰고 1·3을 먼저 진행한다. 화면은 토큰 골격만 만든다 |
| Supabase 프로젝트 URL과 anon 키 | 3 | 마이그레이션·시드 SQL과 훅은 먼저 작성하고, 적용만 보류한다 |
| GitHub 저장소 이름과 공개 범위 | 5 | 5단계 직전에 묻는다. 임의로 정하지 않는다 |

입력이 하나 빠졌다고 전체를 멈추지 않는다. 의존하지 않는 단계는 먼저 끝낸다.

**화면 범위 확정**

Figma 파일에 있는 프레임이 모두 요구사항은 아니다. 채용 과제처럼 원본 시안이 일부 화면뿐이고 나머지는 사용자가 따로 추가한 경우가 있다. 두 종류를 섞으면 시안에 없는 화면을 시안과 대조하거나, 평가 대상 화면의 검증이 얕아진다.

| 구분 | 판단 근거 | 처리 |
| --- | --- | --- |
| 시안 기반 화면 | 원본 시안에 있는 프레임, 디자이너 주석이 붙은 프레임 | 추출·구현·검증 대상. 시안 충실도를 최우선으로 본다 |
| 시안 외 화면 | 사용자가 임의로 추가한 프레임이나 라우트 | 사용자가 반영을 결정하기 전까지 **보류**. 새로 만들거나 고치지 않고, 이미 있는 코드도 지우지 않는다 |

- 어느 쪽인지 코드나 파일로 판단할 수 없으면 사용자에게 묻는다. 임의로 정하지 않는다.
- 확정한 범위는 `_workspace/00_request.md`의 「화면 범위」 표에 적는다. 이후 모든 단계는 이 표를 기준으로 삼는다.
- 사용자가 보류 화면을 반영하기로 하면 표를 고치고 해당 화면만 2 → 3 → 4단계로 실행한다.
- 시안 기반 화면과 시안 외 화면이 충돌하면(공통 위젯의 모양 등) 시안 기반 화면을 기준으로 삼는다.

**작업 공간 생성**

`_workspace/`를 만들고 `_workspace/00_request.md`에 요구사항, 확정한 입력, 화면 범위를 기록한다.

### 1·2단계: 구조 설계와 디자인 추출 (서브에이전트 위임, 병렬)

한 메시지에서 Agent를 두 번 호출한다.

| 에이전트 | `subagent_type` | 프롬프트에 반드시 넣을 것 | 산출물 |
| --- | --- | --- | --- |
| 구조 설계 | `fsd-architect` | 프로젝트 요구사항, Next.js 버전 방침, 작성할 스캐폴딩 범위, 산출 경로 | `_workspace/01_architect_structure.md` |
| 디자인 추출 | `figma-extractor` | Figma URL, 산출 경로 3곳, 화면 범위 표(시안 기반 화면만 추출), 데이터 필드 후보를 반드시 표로 남길 것 | `_workspace/02_figma_*.md` |

두 작업은 서로의 산출물을 참조하지 않는다. 컴포넌트 배치 기준은 양쪽 모두 `fsd-architecture` 스킬의 고정 규칙을 따르므로 순서를 기다릴 필요가 없다.

완료 알림을 기다린다. 알림 전에 결과를 단정하지 않는다. 메인 에이전트가 같은 조사를 중복 수행하지 않는다.

**두 산출물을 받은 뒤 메인이 직접 확인할 것**

- 명세의 화면 수와 라우트 제안이 구조 문서의 `views` 배치 규약과 맞는가.
- 데이터 필드 후보 표가 비어 있지 않은가. 비었으면 3단계에서 스키마를 만들 근거가 없다.

### 3단계: 구현 (지속형 에이전트 협업)

**실행**

`ui-implementer`와 `supabase-engineer`를 이름을 붙여 실행한다. 이 두 역할은 필드 이름과 훅 반환 구조를 서로 맞춰야 하므로 대화 맥락이 유지돼야 한다.

**작업 순서**

1. 리더(메인)가 화면·테이블 단위로 `TaskCreate`에 작업을 등록한다. 의존 관계는 `테이블 → 훅 → 화면` 순으로 건다.
2. `supabase-engineer`가 스키마와 시드를 먼저 확정하고 `_workspace/03_data_contract.md`에 훅 계약 표를 쓴다.
3. 계약이 확정되면 리더가 `SendMessage`로 `ui-implementer`에게 계약 파일 경로와 훅 목록을 전달한다.
4. `ui-implementer`가 화면을 구현한다. 필드가 부족하면 `supabase-engineer`에게 직접 요청한다.
5. 훅 계약이 바뀌면 `supabase-engineer`가 `ui-implementer`에게 먼저 알린다. 말없이 바꾸면 화면이 조용히 빈 값을 렌더링한다.

**통신 규칙**

- 두 에이전트 모두 첫 보고에서 실제로 쓸 수 있는 도구 목록을 리더에게 알린다.
- 리더는 화면 단위 완료 보고를 받을 때마다 4단계 검증을 호출한다. 전부 끝난 뒤 몰아서 검증하지 않는다.
- 같은 파일을 두 에이전트가 동시에 고치지 않게 한다. `src/entities/*`는 데이터 담당, `src/views|widgets|features|shared/ui`는 UI 담당이 소유한다. 소유자가 아닌 쪽은 변경을 요청만 한다.
- 테스트도 소스와 같은 소유 규칙을 따른다. 각 담당은 자기 슬라이스 옆에 `*.test.ts(x)`를 쓰고, 공용 테스트 도구(`test/`)는 데이터 담당이 소유한다. 기능을 바꾸면 테스트도 같이 고친 뒤 완료를 보고한다. 작성 규칙은 `fsd-architecture` 스킬의 `references/testing.md`를 따른다.

**화면이 6개를 넘을 때(선택)**

화면 수가 많고 화면끼리 의존이 없으면, 3단계의 UI 구현만 Workflow로 분산할 수 있다. 사용자가 이 스킬을 호출한 것으로 Workflow 사용에 동의한 것으로 본다.

- `meta.phases`: `['구현', '검증']`
- 구현: `pipeline(screens, s => agent(..., { agentType: 'ui-implementer', isolation: 'worktree' }))` — 병렬 파일 수정 충돌을 막는다
- 검증: 화면마다 `frontend-qa`로 이어서 검사
- 결과 배열에 `.filter(Boolean)`을 적용하고 실패·제외한 화면 수를 `log()`로 남긴다
- 데이터 계약은 분산 전에 **확정돼 있어야 한다.** 계약이 흔들리는 상태로 분산하면 화면마다 다른 필드명을 쓰게 된다

### 4단계: 검증 (서브에이전트 위임)

모듈이 끝날 때마다, 그리고 전체 구현 후 한 번 더 `frontend-qa`를 호출한다.

- 프롬프트에 검증 대상 범위(모듈명 또는 전체), 화면 범위 표 경로(`_workspace/00_request.md`), 계약 파일 경로, 보고서 경로를 적는다. 시안 대조와 화면 상태 검사는 시안 기반 화면에만 한다. 타입·린트·레이어·빌드 검사는 보류 화면을 포함한 전체 코드에 한다. 보류 화면이 빌드를 깨뜨리면 배포할 수 없기 때문이다.
- 보고서의 **높음** 결함은 해당 소유 에이전트에게 `SendMessage`로 넘겨 수정하게 한다. 리더가 직접 고치지 않는다. 고치는 사람과 검증하는 사람이 같으면 검증이 아니다.
- 수정 후 같은 항목을 재검증한다. 수정 주장만 보고 해결로 처리하지 않는다.
- 재검증은 2회까지만 반복한다. 3회째에도 남으면 사용자에게 판단을 요청한다.

### 5단계: 배포 (서브에이전트 위임)

**사용자 승인을 먼저 받는다.** 저장소 생성·푸시·배포는 외부 공개 동작이라 되돌릴 수 없다. 저장소 이름, 공개 범위, 올라갈 내용을 알리고 승인을 받은 뒤에만 `deploy-operator`를 호출한다.

호출 전 조건:

- 4단계 보고서에 높음 결함이 없거나, 사용자가 알고도 배포하기로 했다.
- `npm test`와 `npx next build`가 로컬에서 통과했다.

프롬프트에 저장소 이름, 공개 범위, 등록할 환경 변수 **이름 목록**(값 제외), 보고서 경로를 적는다.

### 6단계: 보고 (메인 에이전트)

사용자에게 다음을 정리해 보고한다.

- 만든 화면과 라우트 목록
- 테이블과 시드 행 수
- QA 결과 요약과 남은 결함
- 저장소 URL, 배포 URL
- **하지 못한 것과 그 이유** — 건너뛴 단계, 검증하지 못한 범위, 보류한 입력

`_workspace/`는 지우지 않는다. 이후 부분 재실행의 근거가 된다.

## 데이터 전달

| 구간 | 방법 | 경로 |
| --- | --- | --- |
| 1·2 → 3 | 파일 | `_workspace/01_*.md`, `_workspace/02_*.md` |
| 데이터 → UI | 파일 + SendMessage | `_workspace/03_data_contract.md` |
| 3 → 4 | 파일 | `_workspace/03_*.md` + 실제 소스 |
| 4 → 3(수정) | SendMessage | 결함 항목을 소유 에이전트에게 |
| 4 → 5 | 파일 | `_workspace/04_qa_report.md` |

파일명은 `{단계}_{담당}_{산출물}.{확장자}` 규칙을 따른다. 최종 산출물은 프로젝트 경로에, 중간 산출물은 `_workspace/`에 둔다.

## 오류 처리

| 상황 | 대응 |
| --- | --- |
| 에이전트 1회 실패 | 한 번만 다시 시도한다. 또 실패하면 그 산출물 없이 진행하고 누락을 보고서에 명시한다 |
| 인증 만료·권한 거부·사용량 한도 | 다시 시도하지 않는다. 결과가 같다. 부분 산출물을 직접 열어 어디까지 진행됐는지 확인하고, 누락 내용을 `_workspace/`에 기록한 뒤 사용자에게 보고한다. 한도라면 해제 시각도 알린다 |
| Figma 추출 실패 | 성공한 화면만으로 3단계를 진행한다. 실패 화면은 구현 대상에서 빼고 목록으로 남긴다 |
| Supabase 미연결 | SQL과 훅은 작성하고 적용만 보류한다. 화면은 로딩·빈 상태까지 확인한다 |
| 빌드 실패 | 타입 검사를 끄거나 설정을 완화해 통과시키지 않는다. 원인 파일을 찾아 소유 에이전트에게 넘긴다 |
| 지속형 에이전트 무응답 | `SendMessage`로 상태를 확인하고 다시 지시한다. 그래도 안 되면 같은 유형을 새 이름으로 실행하고 계약 파일 경로를 프롬프트로 넘긴다 |
| 배포 실패 | `deploy-github-vercel`의 원인 표를 따른다. 같은 명령을 세 번 이상 반복하지 않는다 |

멈춘 에이전트의 빈자리를 메인이 채울 때는 **직접 확인한 사실만** 기록한다. 그 에이전트가 무엇을 왜 제외했는지는 추측해 채우지 않는다.

## 테스트 시나리오

**정상 흐름**

> "이 피그마 시안(URL)으로 상품 목록 화면 만들어줘. Supabase에 더미 데이터 넣고 CSR로 불러와서 보여주고, GitHub에 올려서 Vercel로 배포까지."

기대 동작: 0단계에서 저장소 이름과 공개 범위를 묻는다 → 1·2단계 병렬 실행 → 3단계에서 `products` 테이블과 `useProducts` 계약 확정 후 화면 구현 → 4단계 검증 → 승인 후 5단계 배포 → 6단계에서 배포 URL과 미검증 범위 보고.

**오류 흐름: 디자인은 있고 Supabase 연결 정보가 없음**

> "피그마 시안대로 화면 먼저 만들어줘."

기대 동작: 0단계에서 Supabase 정보가 없음을 확인 → 1·2단계 정상 진행 → 3단계에서 마이그레이션·시드 SQL과 훅 코드는 작성하되 적용은 보류 → 화면은 로딩·빈 상태까지 구현 → 4단계는 데이터 대조를 `검사 불가`로 분류 → 5단계는 사용자 승인이 없으므로 실행하지 않음 → 6단계에서 "Supabase 적용과 배포 보류, 필요한 값 2가지" 를 명시해 보고.

**범위 흐름: 시안 외 화면이 섞여 있음**

> "피그마 시안 반영해줘. 다른 페이지는 아직 넣을지 모르겠어."

기대 동작: 0단계에서 프레임을 시안 기반/시안 외로 나눠 `00_request.md`에 기록 → 2·3단계는 시안 기반 화면만 처리하고 시안 외 화면 코드는 건드리지 않음 → 4단계는 시안 대조를 시안 기반 화면에만 하고 빌드·타입 검사는 전체에 실행 → 6단계에서 보류 화면 목록을 따로 보고.

**후속 요청 흐름**

> "상품 카드에 할인율도 보여줘."

기대 동작: 0단계에서 `_workspace/` 존재 확인 → 부분 재실행으로 판단 → 3단계만 다시 실행(데이터 → UI 순서) → 4단계 재검증 → 배포는 사용자가 요청할 때만.
